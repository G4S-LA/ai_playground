# Оптимизация локальной LLM

Приложение сравнивает два способа обращения к **одной и той же локальной
модели** `qwen2.5:3b`. RAG, облачные модели и внешние API не используются.

```text
один запрос
  ├─ без system prompt + temperature 0.7 + max 1024 + context 8192
  └─ строгий system prompt + temperature 0.1 + max 384 + context 4096
                    ↓
             одна qwen2.5:3b
                    ↓
       ответы, качество, скорость и память
```

Запросы выполняются **последовательно**. Параллельный запуск заставил бы их
конкурировать за CPU/GPU и память и исказил сравнение. Чтобы влияние прогрева
не всегда помогало одному профилю, порядок чередуется: первый запуск идёт
`baseline → optimized`, следующий — `optimized → baseline`.

## Что оптимизировано

| Настройка | До | После | Причина |
|---|---:|---:|---|
| `temperature` | `0.7` | `0.1` | меньше случайности в технических ответах |
| `num_predict` | `1024` | `384` | ограничение лишнего текста и времени генерации |
| `num_ctx` | `8192` | `4096` | короткому техническому вопросу не нужен большой KV cache |
| system prompt | отсутствует | строгий шаблон | разделы «Краткий ответ», «Действия», «Ограничения», до пяти шагов и 220 слов |

Все значения можно изменить через `.env`, не перекомпилируя приложение.

## Квантование

Стандартный Ollama-артефакт `qwen2.5:3b` уже квантован как `Q4_K_M`. Поэтому
приложение не выдаёт существующую квантизацию за новую оптимизацию и не меняет
модель между двумя запросами. Фактические `parameter_size`, `quantization_level`
и размер модели читаются из локального `/api/tags` и показываются в интерфейсе.

Такой дизайн изолирует влияние prompt и generation options. Если преподавателю
нужен отдельный эксперимент именно со степенью квантования, можно дополнительно
сравнить официальные теги `qwen2.5:3b-instruct-q8_0` и
`qwen2.5:3b-instruct-q4_K_M`, но это уже будет второй эксперимент с двумя
артефактами модели.

## Запуск

Требуются JDK 17+, Ollama и уже использованная в предыдущих заданиях модель:

```bash
ollama pull qwen2.5:3b
ollama serve
```

Команды выполняются из `Week_6/thu`.

Проверить локальный runtime, модель и фактическое квантование:

```bash
./gradlew run --args=check
```

Сравнить два профиля через CLI:

```bash
./gradlew run --args="compare Объясни разницу между процессом и потоком"
```

Запустить Web UI:

```bash
./gradlew run --args=web
```

Открыть <http://127.0.0.1:8080>.

## Что показывает сравнение

Для каждого ответа отображаются:

- полный текст ответа для ручной оценки качества;
- простые проверяемые сигналы качества: краткость, структура и наличие раздела «Краткий ответ»;
- общее время, отдельно загрузка модели и генерация;
- количество prompt/response tokens и скорость в tokens/s;
- размер загруженной модели и VRAM по данным локального `/api/ps`;
- параметры профиля, с которыми выполнен запрос.

Сигналы качества не заменяют содержательную оценку: они специально называются
signals, а не «оценкой модели». Для отчёта следует взять несколько одинаковых
технических вопросов, сравнить точность ответов вручную и привести медианные
значения latency и tokens/s после нескольких запусков.

## HTTP API

```text
GET  /api/info
POST /api/compare  {"prompt":"Как безопасно хранить API-ключи?"}
```

`POST /api/compare` возвращает оба ответа, реальный порядок выполнения,
настройки, quality signals и нативные метрики Ollama. Вызовы уходят только на
`http://127.0.0.1:11434` и не содержат облачной авторизации.

## Настройки

| Переменная | По умолчанию |
|---|---|
| `OLLAMA_URL` | `http://127.0.0.1:11434` |
| `OLLAMA_MODEL` | `qwen2.5:3b` |
| `BASELINE_TEMPERATURE` | `0.7` |
| `BASELINE_MAX_TOKENS` | `1024` |
| `BASELINE_CONTEXT_WINDOW` | `8192` |
| `OPTIMIZED_TEMPERATURE` | `0.1` |
| `OPTIMIZED_MAX_TOKENS` | `384` |
| `OPTIMIZED_CONTEXT_WINDOW` | `4096` |
| `OLLAMA_TIMEOUT_SECONDS` | `300` |
| `WEB_HOST` | `127.0.0.1` |
| `WEB_PORT` | `8080` |

Значения читаются из `Week_6/thu/.env`, затем переопределяются переменными
процесса. Пример находится в `.env.example`.

## Автотесты

```bash
./gradlew test
```

Тесты не требуют запущенной Ollama. Они проверяют конфигурацию профилей,
последовательный порядок запросов, его чередование, передачу `temperature`,
`num_predict` и `num_ctx`, чтение квантования и метрик Ollama, а также Web API.
