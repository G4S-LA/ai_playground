# Grounded RAG на Kotlin

Приложение строит ответ только на проверяемых доказательствах из локальной базы знаний. Каждый обычный ответ содержит:

- текст со ссылками `[S1]`, `[S2]`;
- авторитетный список источников: `source`, `section`, `chunk_id`;
- дословные цитаты из соответствующих чанков;
- результат программной валидации.

Если после similarity threshold не осталось ни одного чанка, генерация ответа не запускается. Приложение детерминированно возвращает:

```text
Не знаю: в базе знаний нет достаточно релевантной информации.
Уточните формулировку вопроса или укажите, в каком разделе базы знаний искать ответ.
```

## Pipeline

```text
вопрос
  → query rewrite
  → vector search
  → similarity threshold
  → heuristic reranking
  → structured JSON от LLM
  → проверка sources / [S1] / дословных quotes
  → подтверждённый ответ
```

Модель получает идентификаторы `S1...Sn` и возвращает JSON:

```json
{
  "answer": "Статические данные размещают в префиксе [S1].",
  "sources": [
    {
      "citation": "S1",
      "source": "02-context-engineering.md",
      "section": "Проектирование контекста",
      "chunk_id": "structured-02-context-engineering-004"
    }
  ],
  "quotes": [
    {
      "citation": "S1",
      "quote": "Дословный фрагмент исходного чанка"
    }
  ]
}
```

Приложение не доверяет этому JSON автоматически. Оно проверяет:

1. `answer`, `sources` и `quotes` не пусты;
2. все `[Sx]` существуют среди найденных чанков;
3. ссылки в answer, sources и quotes совпадают;
4. каждая quote дословно содержится в соответствующем чанке.

При ошибке модель получает список нарушений и одну попытку исправления. Если повторный ответ тоже невалиден, приложение создаёт безопасный fallback из дословного фрагмента лучшего источника. Поэтому наружу не выходит ответ с выдуманной цитатой.

## Проверка 10 вопросов

Контрольный прогон проверяет для каждого ответа:

- наличие источников;
- наличие цитат;
- дословное совпадение цитат с чанками;
- согласованность ссылок `[Sx]`;
- наличие ожидаемого файла;
- подтверждается ли смысл ответа цитатами.

Последнюю проверку выполняет LLM-судья, который видит только ответ и цитаты, без внешних знаний. Если ответ судьи невозможно разобрать, используется резервная lexical-проверка. Интерфейс показывает метод и объяснение судьи для ручной проверки.

## Запуск в Windows через MinGW / Git Bash

Нужны JDK 17+, Ollama с `bge-m3` и OpenAI-compatible API:

```bash
ollama pull bge-m3

cd /c/path/to/grounded-rag
cp ../wed/.env .env

./gradlew.bat run --args=web
```

Файл `.env` читается автоматически. Откройте <http://127.0.0.1:8080>.

Если готового `.env` нет:

```bash
cp .env.example .env
# Заполните DOCUMENTS_DIR, INDEX_DB, LLM_API_KEY, LLM_API_URL и LLM_MODEL.
```

Существующий structured-индекс с `bge-m3` переиспользуется. После изменения корпуса или embedding-модели перестройте его:

```bash
./gradlew.bat run --args=index
```

Быстрая проверка без внешнего API:

```bash
./gradlew.bat run --args="web --demo"
```

Demo-модель намеренно не возвращает корректный JSON, поэтому интерфейс продемонстрирует безопасный fallback. Demo-режим требует индекс с demo-эмбеддингами; создать его можно командой `./gradlew.bat run --args="index --demo"`.

## Стоимость оценки

Для одного обычного вопроса выполняются query rewrite и генерация ответа. Контрольный прогон дополнительно вызывает LLM-судью. Таким образом, 10 вопросов требуют минимум 30 API-запросов; при повторной валидации — до 40. Embeddings и vector search выполняются локально.

## HTTP API

```text
GET  /api/info
GET  /api/questions
POST /api/index
POST /api/answer
POST /api/evaluations
GET  /api/evaluations/{id}
```

Пример:

```json
{
  "question": "Как данные следует размещать для эффективного KV Cache?",
  "candidateK": 12,
  "finalK": 5,
  "similarityThreshold": 0.35
}
```
