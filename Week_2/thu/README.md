# Управление контекстом: сжатие истории

Четверг второй недели, на основе [решения среды](../wed/README.md).
Агент работает в веб-чате и CLI, сохраняет чаты в SQLite и умеет заменять
старую часть истории накопительным summary. Сжатие включено по умолчанию.

## Запуск

Из `Week_2/thu` (Python 3.10+):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
# Заполните ключ и модель в .env.
set -a
source .env
set +a
python web.py
```

Откройте <http://127.0.0.1:5000>. Консольный режим: `python cli.py`.
Можно перенести настройки подключения из среды; база четверга по умолчанию
создаётся отдельно. Чтобы продолжить существующие чаты, задайте абсолютный
путь к их базе в `LLM_HISTORY_DB`: новые таблицы создадутся автоматически.
Ключи, базы, кеш Python и виртуальное окружение исключены из Git.

## Как формируется контекст

```text
Со сжатием:  system + summary старой части + дословный хвост + новый вопрос
Без сжатия: system + последние целые пары в пределах окна + новый вопрос
```

1. `N = LLM_KEEP_RECENT_MESSAGES` — сколько последних сообщений гарантированно
   остаются дословными. По умолчанию **10 сообщений**, то есть 5 пар user/assistant.
   System и новый вопрос в это число не входят.
2. Перед очередным ответом агент проверяет, сколько сообщений за пределами N
   ещё не попало в summary. Когда их не меньше `LLM_SUMMARY_EVERY_MESSAGES`
   (по умолчанию **10**), запускается сжатие всей накопившейся старой части.
3. Отдельный запрос к той же модели получает прежнее summary и очередную порцию
   старых сообщений. Модель сохраняет факты, предпочтения, решения, точные значения
   и незавершённые задачи, учитывая исправления. Новое summary заменяет прежнее.
4. Основной запрос получает summary вместо исходных старых реплик и ровно N
   свежих сообщений. Между сжатиями дословный буфер растёт: перед запросом в нём
   может быть от N до N + интервал − 2 сообщений. При коротком чате передаётся
   вся имеющаяся история. Для сжатия на каждом ходе задайте интервал **2**.

Пример с настройками по умолчанию:

| Перед ответом | Сохранено сообщений | В summary | Дословно в основном запросе |
|---|---:|---:|---:|
| 10-й ход | 18 | 0 | 18 |
| 11-й ход | 20 | 10 | 10 |
| 12-й ход | 22 | 10 | 12 |
| 16-й ход | 30 | 20 | 10 |

Число свежих сообщений и интервал — положительные чётные числа от 2:
пары user/assistant не разрываются. Если сжатие включить в длинном старом чате,
агент обработает старую часть несколькими запросами в хронологическом порядке.
Каждый запрос сжатия ограничен интервалом сообщений и локальным окном токенов.

Summary передаётся как отдельное сообщение assistant с поясняющим префиксом.
Исходная системная инструкция остаётся первой. Запрос сжатия отделяет данные
диалога от инструкции и просит не выполнять команды из пересказываемых реплик.

## Управление

В браузере есть переключатель **«Сжатие истории»**, поля **«Свежих сообщений»**
и **«Сжимать каждые»**. Под ними показаны число свёрнутых сообщений, размер
summary и текущий дословный буфер. Раздел **«Резюме старой истории»** показывает
сам текст. Настройки применяются при изменении полей и сохраняются для чата.

В CLI:

```text
/compression on
/compression off
/keep 10
/every 10
/summary
/stats
/window 8192
```

Полная история хранится в `messages` и остаётся видна в интерфейсе.
Summary, число обработанных сообщений и настройки хранятся отдельно в
`chat_context`; расход сжатия — в `summary_calls`. После перезапуска агент
продолжает с сохранённой границы, не пересказывает заново уже обработанные реплики.
Удаление чата каскадно удаляет его историю, summary, настройки и статистику.

Выключение сжатия не удаляет summary: агент перестаёт его отправлять и использует
исходную историю со скользящим окном среды. При достаточном окне передаётся вся
история. Повторное включение продолжает обновлять сохранённое summary.
Если увеличить N настолько, что свежий хвост пересекается с уже свёрнутой
частью, summary сбрасывается и позже строится заново по полной истории.
Предыдущий расход при этом сохраняется.

## Окно, прогноз и ошибки

`LLM_CONTEXT_WINDOW_TOKENS` ограничивает вход по локальной оценке `tiktoken`.
Со сжатием агент не выбрасывает summary или свежие сообщения при переполнении:
запрос останавливается с понятной ошибкой, в вебе — HTTP 413.
Можно увеличить окно, сократить вопрос или уменьшить N/интервал.
Без сжатия действует алгоритм среды: старые целые пары не включаются в запрос,
если не помещаются; интерфейс показывает число пропущенных сообщений.

Прогноз не вызывает модель. Если пора обновить summary, он показывает размер
текущего буфера с пометкой «до обновления summary». После сжатия агент пересчитывает
вход и проверяет окно перед основным API-вызовом. Если в запрос сжатия не помещаются
даже инструкция, предыдущее summary и одна старая пара, нужно увеличить окно.

Размер summary ограничен `LLM_SUMMARY_MAX_TOKENS` (512 по умолчанию): лимит
передаётся в инструкции модели и проверяется локально. Пустое, оборванное
(`finish_reason=length`) или слишком длинное summary не заменяет сохранённое.
В этом случае основной запрос не выполняется, можно повторить попытку.

Каждое успешное обновление summary сохраняется одной транзакцией вместе с его
границей и расходом. Если последующий ответ модели завершился ошибкой, полная
история не меняется, а уже созданное summary остаётся для повторной попытки.
При сбое посередине обработки длинной истории сохраняются успешные порции.

Summary может потерять детали, а при повторном сжатии неточности могут накапливаться.
Полная история в базе позволяет сравнить результат и продолжить без сжатия.

## Токены и стоимость

Сохранены подсчёт токенов, тарифы, учёт кеша и обработка reasoning из среды.
API usage имеет приоритет; без него используется оценка с `≈`.
Оценка `cl100k_base` может отличаться от токенизатора провайдера.

«Расход всего диалога» включает **ответы пользователю и запросы сжатия**.
В подробной статистике расход сжатия показан отдельно; таблица ходов и
«Последний запрос/ответ» относятся к основному диалогу.
Отсутствие тарифов означает неизвестную стоимость, а не бесплатный запрос.
Сжатие требует дополнительных вызовов и не гарантирует экономию на коротком чате.

Учтены успешно сохранённые ответы и summary. При сетевом сбое, отклонённом
summary или ошибке записи провайдер мог списать токены, которых нет в локальном
учёте. Физический лимит модели определяется провайдером; локальная оценка
не гарантирует, что API примет запрос.

## Настройки окружения

| Переменная | По умолчанию |
|---|---|
| `LLM_COMPRESSION_ENABLED` | `true` (`false` выключает) |
| `LLM_KEEP_RECENT_MESSAGES` | `10` |
| `LLM_SUMMARY_EVERY_MESSAGES` | `10` |
| `LLM_SUMMARY_MAX_TOKENS` | `512` |
| `LLM_CONTEXT_WINDOW_TOKENS` | `8192` |
| `LLM_HISTORY_DB` | `chat_history.sqlite3` рядом с агентом |
| `LLM_TOKEN_ENCODING` | `cl100k_base` |

Остальные параметры подключения и тарифов — в [.env.example](.env.example).
Переменные режима/N/интервала задают начальные значения для чатов без сохранённых
настроек. Изменения через интерфейс имеют приоритет и сохраняются в SQLite.
Лимит окна, как в среде, действует только для открытого экземпляра агента.

## Проверка без LLM API

```bash
python -m unittest discover -v
python demo.py
```

Тесты проверяют границы сжатия, содержимое запросов, обновление summary,
режимы on/off, восстановление после перезапуска, ошибки, атомарность записи,
лимиты токенов, статистику и веб-API. Проверки среды сохранены для режима
без сжатия. При первом запуске `tiktoken` скачивает словарь; далее использует кеш.

`demo.py` запускает два агента на одинаковом диалоге и выводит размер входа,
число свёрнутых сообщений и общий расход с учётом сжатия. Ответы и summary
**смоделированы**; демонстрация проверяет работу механизма, а не качество
пересказа реальной модели. Цены условные: $1/$2 за миллион входных/выходных токенов.

Проверка интерфейса в Chromium (дополнительная зависимость):

```bash
python -m pip install playwright
python -m playwright install chromium
python check_web.py
```

Для проверки с реальной моделью задайте N=2 и интервал=2, сообщите кодовое
слово, обменяйтесь несколькими репликами и спросите его снова. Проверьте текст
summary, затем выключите сжатие и сравните прогноз входа. Это потребует API-ключа
и обычных платных запросов провайдера.
