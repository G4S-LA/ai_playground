# Токены, стоимость диалога и локальное окно контекста

Задание среды второй недели. Основа — агент вторника с SQLite, CLI и веб-чатами.
Каждый успешный ход сохраняет сообщения и статистику одной транзакцией.

## Запуск

Из `Week_2/wed` (Python 3.10+):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
# Заполните в .env ключ, модель и при необходимости тарифы.
set -a
source .env
set +a
python web.py
```

Откройте <http://127.0.0.1:5000>. Для консоли: `python cli.py`.

Оба интерфейса работают с реальной моделью и показывают токены и расход:

| Запуск | Где работать | Управление контекстом и статистикой |
|---|---|---|
| `python cli.py` | Терминал | `/window N` меняет окно, `/stats` показывает итоги; после каждого ответа статистика выводится автоматически |
| `python web.py` | Браузер, <http://127.0.0.1:5000> | Поле «Лимит контекста, токены», прогноз перед отправкой и «Подробная статистика» |

В `.env.example` указан DeepSeek, также можно задать другой совместимый
Chat Completions API. Секреты и SQLite не попадают в Git.

При первом использовании `tiktoken` скачивает словарь и кеширует его локально.
Для полностью автономного запуска заранее прогрейте кеш:

```bash
python -c 'import tiktoken; tiktoken.get_encoding("cl100k_base")'
```

## Что считается

| Показатель | Смысл | Источник |
|---|---|---|
| Текущий вопрос | Только текст новой пользовательской реплики | Локальная оценка |
| История | Все сохранённые тексты user + assistant, без system | Локальная оценка |
| Весь вход | System, выбранная часть истории, новый вопрос и обвязка сообщений | До запроса — оценка; после — `usage.prompt_tokens` |
| Пропущено сообщений | Сколько старых сообщений не вошло в запрос | `omitted_history_messages`; в SQLite они сохраняются |
| Генерация | Все токены завершения, включая reasoning, если API включает их в счёт | `usage.completion_tokens` |
| Видимый ответ | Только текст ответа без reasoning | Локальная оценка, `answer_tokens_estimate` |
| Расход чата | Сумма входа и генерации **по всем ходам** | Сохранённые usage каждого хода |

Локальный счёт использует `cl100k_base`: для каждого сообщения добавляются
3 условных служебных токена и токены роли, ещё 3 — на начало ответа.
**Это приближение, особенно для DeepSeek: его токенизатор и шаблон сообщений
отличаются.** Оценки отмечены `≈`; они не выдаются за фактический счёт DeepSeek.
Размер локального окна проверяется именно в единицах этой оценки.

Если API вернул корректные `prompt_tokens` / `completion_tokens`, они имеют
приоритет, даже если отличаются от прогноза. При отсутствии одного из полей
только этот показатель заменяется оценкой. Для генерации она включает
`content` и `reasoning_content`. Источник каждого значения сохраняется как
`api` или `estimate`; reasoning не добавляется к API completion повторно.

Веб-интерфейс показывает прогноз при наборе, заполнение окна и итоги чата.
Над полоской — «Контекст»: оценка входа после подбора последних пар сообщений.
Если старая история не помещается, под полоской показано число пропущенных
сообщений. Модель их не видит, хотя они остаются в чате.
Под ней отдельными строками — «Последний запрос в токенах» и «Последний ответ
в токенах» за последний завершённый ход. Запрос включает весь вход вместе с
выбранной частью истории, ответ — генерацию вместе с рассуждениями; при отсутствии usage
используются оценки с `≈`. До первого ответа показано `—`.
Ниже — «Расход всего диалога»:
сумма токенов всех ходов, включая повторную отправку истории.
Локальный лимит проверяет только вход; приложение не задаёт лимит генерации.
Таблица расхода и объяснение счётчиков находятся в «Подробной статистике».
CLI печатает прогноз и статистику после ответа;
`/stats` повторяет итоги. Статистика восстанавливается после перезапуска.
В старой базе без usage предыдущие ходы обозначаются как неучтённые;
их тексты участвуют в подборе контекста следующих запросов. В колонке
«Пропущено сообщений» у ходов без этого показателя отображается `—`.

После нажатия «Отправить» вопрос сразу появляется в диалоге вместе с надписью
«Модель готовит ответ…». Полученный ответ заменяет эту надпись. При ошибке
неуспешная пара убирается из диалога, а текст вопроса возвращается в поле ввода.

Служебный префикс `</think>` и ведущие блоки `<think>…</think>` удаляются из
видимого ответа. Это также применяется при чтении ранее сохранённых ответов;
исходная запись старого сообщения в SQLite не переписывается. Теги внутри
обычного текста и примеров кода сохраняются. Фактический `usage` не меняется;
если его нет, оценка генерации считает исходный ответ вместе со служебной частью.

## Стоимость

Тарифы задаются в USD за миллион токенов; автоматически не обновляются:

```text
стоимость хода = (
    (вход − кеш) × тариф входа
    + кеш × тариф кешированного входа
    + генерация × тариф выхода
) / 1 000 000
```

Учитывается `prompt_cache_hit_tokens` DeepSeek или
`prompt_tokens_details.cached_tokens` совместимого API. Если нет данных о кеше,
весь вход рассчитывается по обычному тарифу. Если нет тарифа входа/выхода или
API сообщил попадание в кеш без заданного кеш-тарифа, цена хода неизвестна.
Интерфейс отдельно показывает известную сумму и число ходов без цены; `0` в
тарифе означает бесплатные токены, пустое значение — неизвестный тариф.

С каждым ходом сохраняются тарифы и рассчитанная стоимость: изменение `.env`
не переписывает прошлые расходы. Это расчёт по заданным ценам, а не выписка
провайдера: скидки, время суток и другие особенности тарифа нужно учесть при
настройке. Учитываются полученные и сохранённые ответы, включая оборванные.
При сетевом сбое или ошибке записи после генерации расход на стороне провайдера
может уже возникнуть, но локальной записи usage не будет.

## Скользящее окно контекста

```dotenv
LLM_CONTEXT_WINDOW_TOKENS=8192
```

Перед HTTP-запросом агент оставляет системную инструкцию и текущий вопрос,
затем добавляет последние целые пары user/assistant от новых к старым:

```text
инструкция + последние пары сообщений + текущий вопрос <= локальное окно
```

Здесь на вход доступно до 8192 оценочных токенов. System тоже занимает место.
Выбирается непрерывный конец диалога в исходном порядке. Пары не разрываются:
если очередная пара не помещается, она и вся более старая история не отправляются.
Если не помещается даже самая последняя пара, модель получает инструкцию и
текущий вопрос. Сообщения в базе не удаляются и не обрезаются; увеличение окна
снова позволяет включить более старые пары.

Прогноз и реальная отправка используют один алгоритм. `input_tokens_estimate`
считает выбранный вход, `full_input_tokens_estimate` — вход со всей историей,
`included_history_messages` и `omitted_history_messages` — число включённых и
пропущенных сообщений истории. Счёт истории остаётся полным, а расход запроса
берётся из API usage или оценки выбранного входа. Эти показатели сохраняются
для каждого хода.

Размер локального окна остаётся в приложении. Параметр `max_tokens` в API
не отправляется: ограничения генерации определяет провайдер.
Прежняя переменная `LLM_MAX_OUTPUT_TOKENS` больше не читается; её можно
удалить из существующего `.env`.

Окно можно менять в браузере полем «Лимит контекста, токены» или в CLI:

```text
/window 2048
```

Изменение действует для открытого экземпляра чата. После перезапуска или
повторного открытия в CLI используется значение из окружения. Для постоянного
значения измените `.env` и перезапустите приложение.

Если инструкция и текущий вопрос не помещаются даже без истории, агент
поднимает `ContextOverflowError`; веб-API возвращает
HTTP 413 с `code=context_overflow` и прогнозом. HTTP-вызова к модели нет,
сообщения и расход не добавляются; текст остаётся в поле ввода для повторной
отправки. Нужно увеличить окно или сократить вопрос либо инструкцию.

Обычное превышение размера полной истории больше не вызывает ошибку.
При этом модель теряет доступ к исключённым фактам: например, перестанет видеть
имя из начала разговора. Автоматического пересказа старой истории нет.

Настройка не меняет физический максимум модели. Если локальная оценка или
настройка допускает запрос, превышающий реальный лимит провайдера, API может
отклонить его. Агент показывает ошибку, не сохраняя неуспешную пару сообщений.

Отдельный случай — `finish_reason=length`: API сообщает о достижении лимита
длины. Частичный (в том числе пустой) ответ и usage сохраняются, интерфейс
показывает предупреждение с явным указанием на API. Полученный ответ приложение
не обрезает по локальному окну; на следующем ходе он входит в историю и
учитывается при проверке нового входа.

## Воспроизводимый опыт без API-ключа

```bash
python demo.py
```

Используются настоящий агент, временная SQLite и подставной HTTP-клиент.
Ответы **смоделированы**, токены оценены `cl100k_base`; цены условные:
$1 за миллион входных и $2 за миллион выходных. Платных API-вызовов нет.
Результат запуска:

| Ход | Вопрос ≈ | История после ≈ | Вход ≈ | Ответ ≈ | Вне окна, сообщений | Расход токенов ∑ ≈ | USD за ход | USD ∑ |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 11 | 24 | 30 | 13 | 0 | 43 | 0.000056 | 0.000056 |
| 2 | 11 | 48 | 62 | 13 | 0 | 118 | 0.000088 | 0.000144 |
| 3 | 11 | 72 | 94 | 13 | 0 | 225 | 0.000120 | 0.000264 |
| 4 | 11 | 96 | 94 | 13 | 2 | 332 | 0.000120 | 0.000384 |
| 5 | 11 | 120 | 94 | 13 | 4 | 439 | 0.000120 | 0.000504 |
| 6 | 11 | 144 | 94 | 13 | 6 | 546 | 0.000120 | 0.000624 |

Первые три запроса передают всю историю. С четвёртого хода окно уменьшается
до 94 токенов: вход и цена хода перестают расти, старые пары исключаются.
Для одинаковых вопросов и ответов накопленный расход после заполнения окна
растёт линейно. В базе остаются все 12 сообщений: 144 токена сохранённых текстов
и 546 потраченных токенов — разные показатели.

Далее опыт устанавливает окно 22 и отправляет «Продолжай»:

```text
Переполнение локального контекста: инструкция и текущий вопрос ≈23 > окно 22.
Дополнительных HTTP-вызовов: 0; сохранено ходов: 6.
```

После увеличения окна до 23 повторный запрос проходит без старой истории. Последний сценарий
подставляет `finish_reason=length` и показывает частичный ответ с предупреждением.
Проверку реального провайдера можно повторить в веб-чате: несколько одинаковых
вопросов, таблица расхода, затем снижение окна и наблюдение за числом пропущенных сообщений.

## Настройки

| Переменная | По умолчанию в коде |
|---|---|
| `LLM_API_KEY` | Обязательна; альтернатива — `DASHSCOPE_API_KEY` |
| `LLM_API_URL` | `https://api.openai.com/v1/chat/completions` |
| `LLM_MODEL` | `gpt-4o-mini` |
| `LLM_SYSTEM_PROMPT` | Краткий полезный ассистент |
| `LLM_TEMPERATURE` | `0.7` |
| `LLM_TIMEOUT_SECONDS` | `120` |
| `LLM_HISTORY_DB` | `chat_history.sqlite3` рядом с агентом |
| `LLM_CONTEXT_WINDOW_TOKENS` | `8192` |
| `LLM_TOKEN_ENCODING` | `cl100k_base` |
| `LLM_INPUT_PRICE_PER_MILLION` | Неизвестен |
| `LLM_OUTPUT_PRICE_PER_MILLION` | Неизвестен |
| `LLM_CACHED_INPUT_PRICE_PER_MILLION` | Неизвестен |
| `WEB_PORT` | `5000` |

Для OpenAI `gpt-4o-mini` можно выбрать `LLM_TOKEN_ENCODING=o200k_base`;
обвязка сообщений всё равно оценивается приблизительно.

## Проверки

```bash
python -m unittest discover -v
```

Тесты без LLM проверяют рост входа и суммарного расхода, цены и кеш,
приоритет/отсутствие API usage, перезапуск, удаление статистики вместе с чатом,
точную границу окна, блокировку переполнения до сети, повторную отправку,
подбор последних целых пар, сохранение полной истории, восстановление старых
сообщений в контексте после увеличения окна, постоянную цену хода при заполнении окна,
отсутствие `max_tokens` даже со старой настройкой в окружении, сохранение
ответа длиннее 1024 токенов, ошибку контекста провайдера и оборванный ответ. Первый запуск требует
доступа к словарю токенизатора либо заранее прогретого кеша.

Проверка веб-интерфейса в браузере (дополнительные зависимости только для проверки):

```bash
python -m pip install playwright
python -m playwright install chromium --only-shell
python check_web.py
```

Проверяются вопрос и индикатор ожидания до получения ответа, очистка `</think>`,
возврат текста при ошибке, повторная отправка без дубликатов, перезагрузка и
размеры интерфейса на узком экране. Используются подставные ответы без LLM API.
Для сохранения скриншотов добавьте `--screenshots-dir /tmp/wed-web-check`.

Файлы: `agent.py` — запрос и лимит; `token_usage.py` — счёт и стоимость;
`model_output.py` — очистка служебного префикса ответа;
`chat_repository.py` — SQLite; `web.py`, `templates/`, `static/` — веб;
`cli.py` — консоль; `demo.py` — опыт.

Семантика `usage` сверена с
[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/),
повторная отправка истории — с
[Multi-round Conversation](https://api-docs.deepseek.com/guides/multi_round_chat/).
Цены для `.env` берите из
[тарифов провайдера](https://api-docs.deepseek.com/quick_start/pricing/).
