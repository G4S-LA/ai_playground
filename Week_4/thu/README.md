# Автоматический MCP-пайплайн из трёх инструментов

Проект реализует цепочку из MCP tools schemas:

```text
пользователь → модель → search → SearchResult
                              ↓ без изменений
                    summarize → SummaryResult
                              ↓ без изменений
                   saveToFile → файл
                              ↓
                        итоговый ответ
```

Это не три локальные функции, вызванные подряд. Каждый этап зарегистрирован как
отдельный инструмент настоящего MCP-сервера. Агент запускает сервер дочерним
процессом, делает MCP handshake, получает инструменты через `tools/list`,
передаёт их JSON Schemas модели и запускает агентный цикл: модель сама выбирает
следующий инструмент, агент выполняет полученный `tool_call` через `tools/call`,
добавляет результат в историю и снова вызывает модель.

## Инструменты и контракты

| Инструмент | Вход | Результат |
|---|---|---|
| `search` | `query`, `limit` | `SearchResult { query, items[] }` |
| `summarize` | полный `searchResult`, `maxSentences` | `SummaryResult { sourceQuery, sourceCount, summary, sourceIds[] }` |
| `saveToFile` | полный `summary`, `fileName` | `SavedFileResult { path, bytes, sourceCount }` |

Схема `summarize` описывает весь объект, который возвращает `search`, а схема
`saveToFile` — весь объект от `summarize`. Системная инструкция требует передать
объекты целиком. Порядок не зашит в вызовы агента: на каждом ходе модель видит
все три tools и самостоятельно выбирает следующий. После финального ответа
`PipelineAgent` проверяет, что реально получилась цепочка
`search → summarize → saveToFile`.

Поиск сделан по небольшому локальному каталогу, поэтому демонстрация не зависит
от сети. `saveToFile` принимает только простое имя `.md` или `.txt` и не даёт
выйти за пределы `PIPELINE_OUTPUT_DIR`.

## Запуск без API-ключа

Нужен JDK 17 или новее. Из `Week_4/thu`:

```bash
./gradlew run --args=demo
```

Детерминированная demo-модель автоматически вызовет все три MCP-инструмента и
создаст `data/pipeline-report.md`. В консоли будет виден фактический порядок:

```text
1. search
2. summarize
3. saveToFile
Пайплайн завершён: результат сохранён в .../data/pipeline-report.md
```

## Web-интерфейс с живой трассировкой

```bash
./gradlew run --args="web --demo"
```

Откройте <http://127.0.0.1:8080>. Справа отображается цепочка
`search → summarize → saveToFile` и текущее действие агента:

- ожидание ответа модели;
- выбранный моделью `tool_call` и его аргументы;
- выполнение инструмента MCP;
- результат, который возвращается модели;
- переход модели к следующему инструменту или итоговому ответу.

Запуск выполняется в фоновой корутине. Web API сразу возвращает `runId`, после
чего страница опрашивает `/api/runs/{id}` и обновляет трассу примерно раз в
300 миллисекунд. Поэтому панель меняется во время работы модели, а не только
после завершения всего пайплайна.

## Запуск с моделью

Создайте `.env` по образцу `.env.example`, укажите ключ и запустите:

```bash
./gradlew run --args="run Найди материалы про MCP tools, сделай сводку и сохрани её в report.md"
```

Поддерживается любой OpenAI-совместимый Chat Completions endpoint с tool calling.

## Проверка

```bash
./gradlew test
```

Тесты запускают настоящий MCP-сервер по stdio и проверяют:

- наличие трёх инструментов и обязательных полей в их schemas;
- автоматический порядок `search → summarize → saveToFile`;
- точное равенство результата `search` входу `summarize`;
- точное равенство результата `summarize` входу `saveToFile`;
- появление итогового файла и его содержимое;
- Web API асинхронного запуска и события live-трассы модели и MCP tools.
