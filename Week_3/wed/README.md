# Агент с формализованным состоянием задачи

Задание среды третьей недели. Kotlin-агент сохраняет три слоя памяти из
понедельника и дополнительно ведёт состояние каждой задачи как конечный автомат.
Доступны CLI и адаптивный веб-интерфейс на Ktor.

## Конечный автомат

Состояние содержит три обязательных поля:

- `stage` — этап задачи;
- `currentStep` — номер текущего шага (`0` только в состоянии ожидания);
- `expectedAction` — действие, ожидаемое на этом шаге.

Перед запросом агент находится в `idle`. Для простого запроса планирование
пропускается, а для составного выполняется отдельным вызовом модели:

```text
                ┌─→ planning ─┐
idle / new task ┤              ├─→ execution ─→ validation ─→ done
                └──────────────┘       ↑              │
                                      └──────────────┘
```

| Текущий этап | Разрешённый следующий этап |
|---|---|
| `idle` | `planning`, `execution` |
| `planning` | `execution` |
| `execution` | `planning`, `validation` |
| `validation` | `execution`, `done` |
| `done` | нет, это терминальное состояние |

Пользователь не управляет автоматом вручную. Политика сложности выбирает вход в
`planning` либо сразу в `execution`, после чего приложение проверяет каждый
переход. Из `planning` нельзя перепрыгнуть в `validation` или `done`.

Стадии выполняют реальную работу:

1. `planning` — отдельный запрос к LLM составляет план только для сложной задачи;
2. `execution` — отдельный запрос выполняет задачу с учётом плана;
3. `validation` — LLM возвращает `VALID` или замечания `REVISE`;
4. при `REVISE` автомат возвращается в `execution`, исправляет ответ и проверяет
   его ещё раз; при успехе переходит в `done`. Если две проверки подряд требуют
   исправления, агент завершает цикл безопасной просьбой уточнить запрос вместо
   технической ошибки.

Проверяется соответствие черновика исходному запросу, полнота требований и
внутренняя непротиворечивость. Для бессодержательного или неоднозначного запроса
просьба уточнить задачу считается корректным ответом. Внешняя фактологическая
проверка без подключённых инструментов в этот этап не входит.

Состояние хранится отдельно в `data/task-state/<session-id>.json`, удаляется
вместе с диалогом и передаётся модели блоком `[TASK_STATE]`. Модель получает
инструкцию работать в рамках текущего этапа. Фактическая история пройденных
состояний сохраняется с ответом и отображается непосредственно в ленте чата.

## Память

| Слой | Что хранит | Область жизни | Файл |
|---|---|---|---|
| Краткосрочная | текущий диалог и явные заметки | один диалог | `data/short-term/<session-id>.json` |
| Рабочая | цель, контекст, ограничения и текущий план | один диалог/задача | `data/working/<session-id>.json` |
| Долговременная | профиль, решения и знания | все диалоги | `data/long-term/memories.json` |

Обычная переписка автоматически сохраняется только в краткосрочную память.
Пользовательские записи памяти выполняются явно. Для сложного запроса агент явно
сохраняет созданный план в рабочую память как `agent_plan`; перед следующим
запросом заменяет или удаляет только эту служебную запись, не затрагивая записи
пользователя.

Prompt собирается в фиксированном порядке:

```text
system instruction
[LONG_TERM_MEMORY]
[WORKING_MEMORY]
[TASK_STATE] stage + current_step + expected_action
short-term dialogue
current user query
```

## Запуск

Нужна JDK 17+. Из `Week_3/wed`:

```bash
./gradlew test
./gradlew run --args="cli --demo"
./gradlew run --args="web --demo"
```

В Windows MinGW/Git Bash используйте `./gradlew`, в PowerShell —
`.\gradlew.bat`. Веб доступен по адресу <http://127.0.0.1:8080>.

Для реальной OpenAI-совместимой модели скопируйте `.env.example` в `.env` и
заполните ключ. Кавычки вокруг значений необязательны:

```dotenv
LLM_API_KEY=...
LLM_MODEL=gpt-4o-mini
```

Переменные процесса имеют приоритет над `.env`. Gradle 9.7.1 официально
запускается на JDK 17–26; Java 27 пока находится вне его матрицы совместимости.

## Состояние в CLI

```text
/state
```

`/state` показывает последнее состояние. CLI печатает этап в момент его
фактического начала. Для простого запроса `planning` не появляется.

Остальные команды памяти и диалогов: `/remember`, `/memory`, `/forget`, `/new`,
`/sessions`, `/use`, `/delete`, `/help`, `/exit`.

Веб-версия во время обработки опрашивает текущее состояние и выделяет каждый
фактически запущенный этап отдельным маркером между сообщением пользователя и
ответом агента. Справа находится только read-only индикатор текущего этапа, шага
и ожидаемого действия. Если запрос сразу перешёл в `execution`, неприменённый
`planning` остаётся серым и зачёркнутым. Вводить состояние вручную не требуется.
Ниже сохранены слои памяти и форма явной записи. Подсчёта токенов, копирования
диалога и настроек стратегии контекста нет.
