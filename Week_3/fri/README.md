# Агент с глобальным жизненным циклом задачи

Задание пятницы третьей недели. Состояние относится ко всей задаче и живёт
между запросами пользователя, а не изображает внутренние шаги одного ответа.
Планирование отделено от выполнения явным approval gate.

## Основной сценарий

```text
новая задача
    │
    ▼
 planning ── замечания пользователя ──┐
    ▲                                 │
    └──────── обновлённый план ───────┘
    │
    │ явное /approve или кнопка «Утвердить план»
    ▼
 execution ────────────────┐
    │                      │ замечания проверки
    ▼                      │
 validation ── REVISE ─────┘
    │
    │ VALID
    ▼
   done
```

Первое сообщение только создаёт план. Агент сохраняет исходную задачу как
`agent_task`, план как `agent_plan`, показывает план пользователю и остаётся в
`planning`. Пока план явно не утверждён, `execution` недоступен.

На этапе `planning` обычное сообщение считается замечанием к плану: модель
пересоставляет его, но по-прежнему не начинает реализацию. Утверждение —
отдельное действие:

- CLI: `/approve`;
- Web: кнопка «Утвердить план и выполнить»;
- API: `POST /api/sessions/{id}/tasks/approve`.

После approval агент реализует сохранённую исходную задачу и проверяет результат
относительно поставленной цели. При `REVISE` автомат возвращается в `execution`,
модель исправляет результат и снова запускает `validation`. Только `VALID`
открывает переход в `done`.

Если две проверки подряд неуспешны, задача переходит в `blocked`. Следующее
сообщение пользователя становится уточнением, после чего выполнение
возобновляется. Ошибка модели переводит текущую задачу в `failed`; незавершённый
черновик не выдаётся за результат.

## Состояния и события

| Состояние | Разрешённые события | Результат |
|---|---|---|
| `idle` | `start_task` | `planning` |
| `planning`, план создаётся | `plan_ready`, `block`, `fail` | ожидание approval, `blocked` или `failed` |
| `planning`, план готов | `approve_plan`, `revise_plan`, `block`, `fail` | `execution`, новый план, `blocked` или `failed` |
| `execution` | `complete_execution`, `block`, `fail` | `validation`, `blocked` или `failed` |
| `validation` | `pass_validation`, `reject_validation`, `exhaust_validation`, `block`, `fail` | `done`, `execution`, `blocked` или `failed` |
| `blocked` | `resume`, `fail` | восстановление этапа или `failed` |
| `failed` | `retry`, `start_task` | повтор этапа или новая задача |
| `done` | `start_task` | новая задача с `planning` |

Переход задаётся бизнес-событием, а не желаемым target stage. Запрещённое
событие возвращает причину и список допустимых событий, не изменяя сохранённое
состояние.

## Запуск

Нужна JDK 17+. Из `Week_3/fri`:

```bash
./gradlew test
./gradlew run --args="cli --demo"
./gradlew run --args="web --demo"
```

Пример CLI-диалога:

```text
Вы: Реализуй консольный менеджер задач
Агент: 1. Определить модель... 2. Реализовать команды... 3. Проверить...
Вы: Сначала добавь тесты в план
Агент: 1. Написать тесты... 2. Реализовать команды... 3. Проверить...
Вы: /approve
[execution] ...
[validation] ...
Агент: <проверенный результат>
```

Для реальной OpenAI-совместимой модели скопируйте `.env.example` в `.env` и
задайте ключ. Веб-интерфейс доступен на <http://127.0.0.1:8080>.

## Что проверяют тесты

- после создания плана задача остаётся в `planning` между запросами;
- approval до готовности плана отклоняется;
- замечания меняют план, но не запускают реализацию;
- только явный approval открывает `execution`;
- `done` недостижим без успешного `validation`;
- замечания проверки возвращают `validation → execution`;
- исчерпание попыток ведёт в `blocked`, а уточнение возобновляет задачу;
- запрещённое событие не изменяет сохранённое состояние.
