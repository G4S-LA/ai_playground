# Агент с контролируемым жизненным циклом задачи

Задание пятницы третьей недели. Здесь автомат из среды расширен именно
**негативными сценариями**: переход задаётся доменным событием, недопустимое
событие отклоняется без изменения состояния, ошибки и исчерпание повторных
проверок представлены отдельными состояниями.

## Отличие от среды

В среду был реализован основной маршрут:

```text
planning → execution → validation → done
```

Пятница отвечает на вопрос «что произойдёт, если маршрут нарушен или этап не
удался?». Вызывающий код больше не передаёт желаемый следующий этап строкой.
Он отправляет событие (`approve_plan`, `complete_execution`,
`pass_validation`), а единственный `TaskStateMachine` определяет следующий
этап. Благодаря этому нельзя напрямую присвоить `done`.

Перед стартовым событием отдельный LLM-router оценивает сложность запроса. Он
возвращает только `PLAN` или `DIRECT`: большие, многошаговые, архитектурные и
рискованные задачи начинают путь с `planning`, а короткие и простые — сразу с
`execution`. Текст пользователя передаётся router-у как данные, поэтому просьба
«пропусти планирование» не управляет автоматом напрямую. При ошибке или любом
другом ответе модели применяется детерминированная `RequestComplexityPolicy`.

```text
user request → LLM planning router → PLAN   → planning → execution
                                └──→ DIRECT → execution
```

## Состояния и события

| Состояние | Разрешённые события | Результат |
|---|---|---|
| `idle` | `start_with_plan`, `start_without_plan` | `planning` или `execution` |
| `planning` | `approve_plan`, `block`, `fail` | `execution`, `blocked` или `failed` |
| `execution` | `complete_execution`, `request_replanning`, `block`, `fail` | `validation`, `planning`, `blocked` или `failed` |
| `validation` | `pass_validation`, `reject_validation`, `exhaust_validation`, `block`, `fail` | `done`, `execution`, `blocked` или `failed` |
| `blocked` | `resume`, `fail` | восстановление этапа или `failed` |
| `failed` | `retry`, `start_with_plan`, `start_without_plan` | повтор этапа или новый цикл |
| `done` | `start_with_plan`, `start_without_plan` | новый цикл |

Главные гарантии:

- после `planning` выполнение начинается только событием `approve_plan`;
- `done` достижим только событием `pass_validation` из `validation`;
- `reject_validation` возвращает задачу в `execution`;
- две неуспешные проверки переводят задачу в `blocked`, а не маскируются под
  успешное завершение;
- следующее уточнение пользователя выполняет `resume` и продолжает задачу;
- ошибка модели переводит активную задачу в `failed`, незавершённый черновик не
  сохраняется как ответ;
- отклонённое событие возвращает причину и список допустимых событий, а
  сохранённое состояние остаётся прежним.

`TaskState` дополнительно хранит `planApproved`, число попыток проверки,
`recoveryStage` и причину последней остановки. Эти данные видны через CLI
`/state`, API и веб-интерфейс.

## Запуск

Нужна JDK 17+. Из `Week_3/fri`:

```bash
./gradlew test
./gradlew run --args="cli --demo"
./gradlew run --args="web --demo"
```

Веб-интерфейс доступен на <http://127.0.0.1:8080>. Для реальной
OpenAI-совместимой модели скопируйте `.env.example` в `.env` и задайте ключ.

## Что проверяют тесты

- запрет реализации до утверждения плана;
- выбор моделью между планированием большой задачи и прямым выполнением простой;
- запрет `done` без валидации;
- неизменность состояния после запрещённого события;
- возврат `validation → execution`;
- переход в `blocked` после исчерпания попыток и последующий `resume`;
- переход в `failed` при технической ошибке и возможность `retry`;
- полный happy path через CLI/API-уровень агента.
