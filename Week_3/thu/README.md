# Агент с обязательными инвариантами

Задание четверга третьей недели. За основу взят агент с явной памятью из
`Week_3/mon`, но инварианты намеренно вынесены в отдельную сущность и отдельный
этап обработки ответа.

## Чем инвариант отличается от рабочей памяти

Рабочая память отвечает на вопрос **«что сейчас важно знать о задаче?»**.
Инвариант отвечает на вопрос **«какие решения вообще недопустимы?»**.

| | Рабочая память | Инвариант |
|---|---|---|
| Назначение | контекст текущей задачи | граница допустимых решений |
| Время жизни | один диалог/задача | все диалоги |
| Приоритет | может уточняться новым контекстом | выше запроса, диалога и памяти |
| Реакция на конфликт | ассистент выбирает релевантный контекст | ответ блокируется, возвращается отказ |
| Хранение | `data/working/<session-id>.json` | `data/invariants/invariants.json` |

Например, `«дедлайн — пятница»` — рабочая память: в следующей задаче он будет
другим. `«платёжные данные нельзя писать в логи»` — инвариант: просьба
пользователя показать удобный способ такого логирования должна получить отказ.

Поле `constraint` в рабочей памяти сохранено для локальных ограничений задачи,
но оно не заменяет инвариант. Это изменяемый контекст, а не обязательная
постусловная проверка.

## Как обеспечивается соблюдение

Обработка запроса состоит из двух независимых вызовов:

```text
запрос + память + [NON_NEGOTIABLE_INVARIANTS]
                    │
                    ▼
             черновик модели
                    │
                    ▼
       guard проверяет каждый invariant id
              │                 │
          compliant      violation / ошибка
              │                 │
       вернуть черновик     скрыть черновик
                            вернуть отказ
```

1. `PromptBuilder` передаёт инварианты отдельным системным блоком раньше памяти
   и явно задаёт их приоритет.
2. `InvariantGuard` получает запрос, черновик и полный список инвариантов. Он
   обязан вернуть структурированную проверку для каждого `id`.
3. При `violation` черновик не отдаётся пользователю. При некорректном или
   неполном отчёте действует fail-closed режим: ответ тоже блокируется.
4. Краткий результат проверки сохраняется вместе с ответом и виден в CLI и
   веб-интерфейсе. Это показывает, какие правила были учтены, не раскрывая
   внутреннюю цепочку рассуждений модели.

Инварианты не извлекаются автоматически из переписки: их можно изменить только
явной CLI-командой или отдельным API-запросом. Удаление диалога удаляет его
краткосрочную и рабочую память, но не затрагивает инварианты.

Проверка инварианта, записанного естественным языком, не является формальным
доказательством. Здесь используется независимая LLM-проверка и безопасный отказ
при любой ошибке её протокола. Для правил, которые можно выразить кодом
(allowlist зависимостей, JSON Schema, лимиты), в production их также следует
дублировать детерминированными валидаторами.

## Запуск

Нужна JDK 17+. Из `Week_3/thu`:

```bash
./gradlew test
./gradlew run --args="cli --demo"
./gradlew run --args="web --demo"
```

Веб-интерфейс откроется на <http://127.0.0.1:8080>. В нём инварианты визуально
отделены от памяти, а под каждым ответом доступен отчёт проверки.

Демо работает без внешнего API и распознаёт простые правила вида
`«Запрещено использовать X»` / `«Не использовать X»`. Например:

```text
/invariant add stack_constraint Запрещено использовать Python
Предложи использовать Python
```

Для полноценной семантической проверки скопируйте `.env.example` в `.env`,
задайте ключ OpenAI-совместимого API и запустите без `--demo`:

```bash
cp .env.example .env
./gradlew run --args="web"
```

## CLI-команды

```text
/invariant add <architecture|technical_decision|stack_constraint|business_rule> <текст>
/invariant remove <invariant-id>
/invariants
/remember short_term dialogue_note <текст>
/remember working <goal|context|constraint|note> <текст>
/remember long_term <profile|decision|knowledge> <текст>
/memory [all|short_term|working|long_term]
/forget <layer> <memory-id>
/new
/sessions
/use <session-id>
/delete
/help
/exit
```

## Основные API-маршруты

```text
POST   /api/sessions/{id}/invariants
DELETE /api/sessions/{id}/invariants/{invariantId}
POST   /api/sessions/{id}/messages
GET    /api/sessions/{id}
```

`POST .../messages` возвращает не только `answer`, но и `compliance` со
статусом, итогом и проверкой каждого активного инварианта.
